# 执行摘要

核心结论

现有 JU 工作台的瓶颈不在存储，在运行时——每次打字触发 4 处全量深拷贝 + 2 处全表遍历 + 1 次全量序列化，20k 节点即明显卡顿。要支撑「大数据量 + 长期流畅 + 桌面客户端」，必须在架构层完成 8 项解耦改造，其中 2 项为 P0 必做（commit 结构共享、历史栈增量），可在 2 周内把日常写作从卡顿拉到无感；其余 6 项按需分阶段推进。商业化解锁由三门控（合规门 G0 + 稳定性门 G2 + 规模门 G2′）共同决定。

关键指标：2 周 P0 改造（结构共享+历史栈）；3–10 万 目标支撑节点数；7–10 月 总工期（乐观/现实）；¥4.3–17 万 总预算区间（含合规）。

付费设计：核心本地功能永久免费，只对 Sync/Publish/团队等增值服务收费；收费上线由 G0+G2+G2′ 三门控决定；G3 付费转化 >0.5%，G4 月活留存 >30% 且 NPS≥30。

## 六条判断

1. 硬约束全量深拷贝是全局限速器。只要 safeClone(state) 与 JSON.stringify(state) 仍在主路径，任何节点规模都无法流畅。

2. 可解结构共享 + 增量落盘 + 增量索引 + 虚拟滚动四项做完，10 万节点可流畅；只做前两项，3 万节点可流畅。

3. 风险优化不是免费的。增量落盘与增量索引有静默不一致风险；内存工作集是范式转变（同步变异步），是最贵的一项。

4. 门控合规是商业化前置门，不是工程完成后才做。商标、开源许可、隐私、商用密码、FTO 高风险项必须在收费上线前处理；新增 G0 合规门，与 G1/G2/G2′ 并列。

5. 节奏商业化不等工程全做完。用 waitlist 在 M1–M3 提前测付费意愿；收费上线由 G0 + G2 + G2′ 三门控决定。

6. 已实现十余项防御性优化已在代码中。墓碑防复活、侧栏指纹、LRU 缓存、原型污染防御、加密兜底、多标签 LWW 等已就位，报告性能清单须与代码对齐，避免重复投入（详见附录 A / B）。

边界：所有工期与成本为单人+AI协作、兼职投入假设下的估算；性能数字为规划目标（基于现有代码盘点与业界同类操作基准），非实测值。

# 一、现状盘点：瓶颈在哪里

术语约定

节点数：state.nodes 中的节点总数（含文件夹/日历待办/数据库行）。

文档：根节点的直接子节点；一个文档 = 一棵子树。文中“大文档”统一改为“大库”。

大库：指目标规模 3–10 万节点。

已实现 / 部分 / 未修：以 2026-10-07 代码盘点为准，状态标签见各表。

## 1.3 支撑上限结论

| 维度 | 现状 | 结论 |
| --- | --- | --- |
| 存储上限 | 浏览器 localStorage 约 4.5MB（≈2–3 万纯文本节点）；Tauri SQLite 无硬限 | 浏览器版大量内容直接不可用 |
| 流畅度 | 全量常驻内存；≥2 万节点启动慢、搜索/标签/日历全表遍历、撤销栈巨大 | 必卡 |
| 稳定性 | 内存常驻 state，大库 OOM 风险；有崩溃兜底但重启慢 | 长期不稳 |
| 兼容性 | Chrome/Edge 全支持；Safari 部分 CSS 降级；Tauri 三平台 | 无额外问题 |

一句话诊断

桌面版绕开了存储限制，但没有绕开运行时限制——safeClone / renderMain / JSON.stringify 一个没少。瓶颈已从「存不下」转移到「跑不动」。

# 二、D0 规模决策：两条改造路线

在 M1 开工前必须定路线，因为它决定 M1 的范围、工期、成本与交付形态。

| 维度 | 路线 A · 低侵入改造 | 路线 B · 深度重构 |
| --- | --- | --- |
| 做法 | 结构共享 + 历史栈增量 + 落盘增量 + 增量索引 + 分片导入 + 内存监控 + 大库模式开关 | 在 A 基础上加 DAO 持久访问层 + 索引落地 SQLite/IndexedDB + 按需加载（内存工作集）+ 同步重构 |
| 支撑上限 | Tauri 5–10 万；浏览器上限不变（仍受 5MB） | Tauri 数十万–百万；浏览器突破 5MB（IndexedDB） |
| 工作量 | 2–4 周（AI 下约 2 周） | 8–12 周，返工 30–40%（并入 M1–M2） |
| 隐性 bug 风险 | 中：撤销差分、增量索引易出错 | 高：数据迁移、并发读写、索引一致性、同步变异步 |
| 交付形态 | 维持单 HTML | 多文件工程，单 HTML 交付消失 |
| 用户体验 | 大库变快但上限仍在；大库模式关闭部分功能 | 大库体验质变；批量操作异步化需 loading |
| 兼容性 | 完全向后兼容 | 旧数据需迁移层；老浏览器 IndexedDB 受限 |
| 适用判据 | 目标用户 >2 万节点占比 <20%，或桌面为主形态 | 目标用户 >2 万节点占比 >20%，或明确对标 Obsidian 规模 |

推荐路径

默认先 A，预留 B 的升级接口。原因：A 的风险可控、向后兼容、2 周可交付；B 的核心风险（内存工作集导致同步变异步）会波及所有 N(id) 调用点，返工面极大。M5 用户验证若出现规模化投诉，再启动 B。

合规对路线选择的影响

若选择路线 B（IndexedDB / DAO / 按需加载），需同步评估：① 加密模式下的分页解密与索引一致性；② 多标签同步从 storage 事件改为 BroadcastChannel + patch 重放；③ 隐私政策中数据存储位置与跨境传输。路线 A 的合规面更小，建议默认先 A。

## 可支撑节点上限对比

横轴为对数刻度（1 万–40 万节点）；浏览器版受 5MB localStorage 硬限，仅路线 B（IndexedDB）可突破。

# 三、分层优化方案（8 层解耦）

核心原则：让每个操作的复杂度与总节点数解耦。从下到上 8 层，每层标注改动、收益、代价、风险。P0 = 必做，P1 = 强烈建议，P2 = 按需，P3 = 规模化后再做。

### L1 · 存储层 —— 从「一坨 JSON」到「关系表」P2

浏览器：localStorage → IndexedDB；桌面：SQLite 单表 → WAL + 分页

| 项 | 内容 |
| --- | --- |
| 改动 | nodes 表主键 id，索引 parent；不再把 state.nodes 序列化成一个 JSON 串；支持游标分页读取 |
| 收益 | 浏览器突破 4.5MB；大库启动从「全量读」变「按需读」 |
| 代价 | 首屏变异步（IndexedDB 是异步 API）；storage 事件失效（多标签同步少一道保险）；Safari IndexedDB 历史 bug；隐私模式下不可用 |
| 风险 | 迁移失败丢数据；多标签同步静默失效 |
| 工期 | 2 周（含迁移 + 回滚演练） |

### L2 · 内存模型 —— 从「全量常驻」到「工作集」P3 · 最贵

内存中只保留视口附近 ±N 节点 + LRU 热点；其余按需从存储层加载

| 项 | 内容 |
| --- | --- |
| 改动 | nodesCache = LRU Map（上限 5,000）；访问未命中 → 异步加载 → 占位符 + 骨架屏；屏外节点释放引用 |
| 收益 | 内存占用与视口大小成正比，与总节点数无关（封顶 200MB） |
| 代价 | 同步 API 变异步：N(id) 从同步返回变 await，所有调用点要改；docWordCount / docSubtree 等递归函数失效，要改成数据库聚合或维护缓存计数 |
| 风险 | 范式转变，返工面最大；崩溃恢复时内存不完整；加密模式逐节点解密？还是解密后分页？两种都要重设计 |
| 工期 | 3 周（AI 协作），返工 40% |

### L3 · 状态变更 —— 从「全量克隆」到「结构共享」P0 · 必做

commit 只复制变更路径，其余节点引用不变

| 项 | 内容 |
| --- | --- |
| 改动 | 引入 Immer（~15KB）或自研 immutable；produce(state, draft => { draft.nodes[id].text = newText })；节点带 _version 供视图 diff |
| 收益 | 打字从 100–300ms 降到 5ms；视图 diff 变 prev.nodes[id] !== next.nodes[id] |
| 代价 | 引入新依赖；200+ 处 commit 回调要验证（delete、数组 splice 在 Proxy 下行为不同）；safeClone 的 JSON 降级路径失效 |
| 风险 | 引用语义 bug：若任何代码原地改旧 state（light 模式现在就这么干），历史栈会被污染 |
| 工期 | 1 周 |

### L4 · 撤销栈 —— 从「全量快照」到「逆操作」P0 · 必做

存 patch 不存快照

| 项 | 内容 |
| --- | --- |
| 改动 | undo 栈记录 {id, field, prevValue}；redo 栈记录 {id, field, nextValue}；批量操作的逆操作要记录每个节点的原 parent + 原 index + 原顺序 |
| 收益 | 撤销栈内存从 600MB 降到 <1KB；undo O(1) |
| 代价 | 结构性操作（删子树、批量移动）的逆操作复杂；noHistory 提交的「缺环」处理；加密明文兜底 _pendingPlainState 依赖全量引用 |
| 风险 | 逆操作对称性 bug；撤销后无法回到中间态 |
| 工期 | 3–5 天 |

### L5 · 渲染 —— 从「全量重建」到「真虚拟滚动」P1 · 部分实现

现状：content-visibility 弱虚拟滚动已就位；真虚拟滚动（DOM 复用）待做

| 项 | 内容 |
| --- | --- |
| 已实现 | content-visibility:auto + contain-intrinsic-size + .outline.virtual；VIRTUAL_THRESHOLD=200 自动启用；_virtualDisabled 降级路径；@supports 包裹兼容旧浏览器；.node.has-children 估算高度 |
| 待做 | 绝对定位 + transform: translateY(offset) 撑开滚动条；滚动事件（throttle 16ms）计算可视区间；复用 DOM 元素换内容；renderMain 改 changedIds 增量 patch |
| 已实现收益 | 屏外行渲染跳过，20k 节点首屏明显改善（具体数值待实测） |
| 待做收益 | 首屏从 O(n) 变 O(viewport)；10 万节点也能开；切视图从 300–800ms 降到 <100ms |
| 代价 | 大纲整个视图重写；拖拽跨屏失效；Ctrl+F 浏览器原生搜索失效；选区跨屏失效；打印要临时全量渲染 |
| 风险 | 交互退化：拖拽、多选、折叠、Tab 缩进全部要重写 |
| 工期 | 3–4 周（含所有交互重写） |

### L6 · 索引 —— 从「全量重建」到「增量维护」P1 · 强烈建议

日历 / 标签 / 反链 / 搜索四个索引按 changedIds 增量更新

| 项 | 内容 |
| --- | --- |
| 改动 | date → [id] 反向表；tag → [id] 反向表；targetTitle → [sourceId] 邻接表；搜索倒排索引（词 → [id]）；每次 commit 携带 changedIds，只更新这些 id 的条目 |
| 收益 | 切视图从 500ms 降到 100ms；搜索从 200–500ms 降到 <100ms |
| 代价 | 索引一致性风险（漏更新就长期错误）；删除子树的连锁反应（要更新 4 个索引）；首次加载要从空构建 |
| 风险 | 静默错误：用户不会立刻发现「某条待办不出现在日历里」，几周后才发现数据「看起来丢了」 |
| 工期 | 2 周 |

### L7 · 计算 —— 从「主线程」到「Worker」P2 · 部分实现

现状：图谱 Barnes-Hut 布局已 Worker 化；日历/搜索/导出/导入仍待迁

| 项 | 内容 |
| --- | --- |
| 已实现 | GraphLayoutWorker + GRAPH_WORKER_SRC 内嵌 Worker；Transferable 零拷贝；pause/resume；连续 2 次超时自动 terminate 重建（timeoutStrikes）；同步回退路径 runSyncGraphLayout |
| 待做 | 日历索引重建、搜索、导出序列化、导入解析、版本快照加密全部进 Worker；用 Transferable（ArrayBuffer）零拷贝传大对象 |
| 已实现收益 | 图谱布局不卡主线程；大图（≤300 节点）可交互 |
| 待做收益 | 搜索/导出/导入不冻结 UI |
| 代价 | 数据序列化成本；索引查询变异步 → 渲染要分两阶段（先骨架后填充）→ 面板闪烁；Worker 生命周期管理；部分环境受限 |
| 风险 | 渲染闪烁；Worker 里的错误堆栈跨线程难调试 |
| 工期 | 2 周 |

### L8 · IO —— 从「全量序列化」到「增量 patch」P1 · 强烈建议

只传变更节点，不传整棵树

| 项 | 内容 |
| --- | --- |
| 改动 | 维护 dirtyNodes / removedNodes 集合；落盘时 desktopInvoke('patch_nodes', {changed, deleted})；桌面 SQLite UPDATE nodes SET data=? WHERE id=?，每条 O(1)；配合 WAL 先写日志再批量提交 |
| 收益 | 落盘从 1s 降到 50ms；与总节点数解耦 |
| 代价 | 多标签合并语义变化（接收方要重放 patch）；崩溃恢复要维护 patch 日志 + 定期全量 checkpoint；加密模式要么每条 patch 单独加密（开销大）要么维护加密 patch 链（复杂） |
| 风险 | 多标签静默不一致：patch 顺序不同或丢一条，比现在「整体覆盖」更难排查 |
| 工期 | 1–2 周（含 Rust 侧改动） |

| P1c | L5 真虚拟滚动 | ⚠️ content-visibility | 首屏 O(1)；10 万节点可用 | 3–4 周 | 中 | P1b 稳定后 |
| P2 | L7 Worker 化 | ⚠️ 图谱已 Worker | 主线程不卡 | 2 周 | 中 | 用户投诉卡顿时 |
| P3a | L1 IndexedDB | ❌ | 浏览器突破 4.5MB | 2 周 | 高 | 浏览器用户 >2 万节点 |
| P3b | L2 内存工作集 | ❌ | 内存封顶 200MB；百万节点 | 3 周 + 40% 返工 | 极高 | 路线 B 决策后 |

关键判断

只做 P0（1.5 周）：20k–30k 节点流畅，打字无感。这是投入产出比最高的一步。

    做 P0 + P1a + P1b + P1c（约 8 周）：10 万节点流畅，桌面版达到「长期大量写作」标准。

    再做 P2 + P3：百万节点，但风险陡增，建议等真实用户验证。

# 四、三轨融合路线（M0–M5）

## 4.1 六条融合原则

1. 解耦「可收费」与「可稳定」与「可合规」：三件事并行，收费由门控决定。

2. 采纳工程优先的结构与门控（M0–M4），并入商业前置（许可/定价/支付/落地页/内测）与合规前置（商标/FTO/开源/隐私/密码）。

3. 单一门控口径：合规门 G0 + 稳定性门 G2 + 规模门 G2′ + 商业门 G3/G4 统一。

4. 合规不单独占用关键路径：与工程并行，但 G0 必须在 M4 结束前完成，否则不得收费上线。

5. 以代码现状为基线：报告 §1.2 / §3 的状态标签以 2026-10-07 代码盘点为准，已实现项不再进入排期；附录 A 为逐条对照依据。

## 4.6 付费相关功能设计（Track B 核心）

### 4.6.1 设计原则

1. 核心本地功能永久免费：本地编辑、9 类视图、插件、加密、导入导出、P0/P1 性能优化（结构共享、历史栈增量、增量落盘、增量索引、虚拟滚动）不设付费墙。

2. 只对托管与增值服务收费：同步、发布、版本历史延长、团队协作、权限审计、优先支持等。

3. 数据主权不因付费改变：所有付费服务必须支持完整导出；Sync 端到端加密；Publish 可一键下线；取消订阅不删除本地数据。

4. 付费不进入关键路径：M1–M3 用 waitlist 测付费意愿；M4 支付与授权码就绪；M5 内测收费试点。

5. 门控决定收费上线：G0 合规门 + G2 稳定性门 + G2′ 规模门全部通过后，才允许收费上线；G3/G4 验证转化与留存。

6. 自愿支持与商业授权并行：设 Supporter 一次性支持者方案，商业授权参考行业惯例但可非强制，主要用于企业合规采购与发票。

### 4.6.3 支付、授权与生命周期

# 六、合规与知识产权风险（融合版）

商业化不是“工程做完再补合规”，而是与工程加固线并行的第三道门控。本章把专利 FTO、商标、开源许可、隐私、商用密码、AI 代码、地图残留、第三方数据八类风险，按“影响功能 → 解决方法 → 难度 → 商业化/自用”统一纳入执行方案。

免责声明（合规部分不构成法律意见）

本报告合规结论基于 2026-10-07 检索结果，不构成法律意见。FTO 结论的法律状态、同族、保护期与权利要求原文需由专利律师核验；商标结论待第 9 类补充；开源许可、隐私、商用密码、AI 代码结论需在 SBOM、合规评估与 SCA 查重完成后更新。具体行动前请咨询专业律师。

核心结论

不存在绝对无解的问题，但存在“必须放弃某项功能”或“必须支付许可费”的选择。唯一硬约束是商标：若“JU”“桔”在核心类别已被注册且无法改名，则商业化路径受阻。其余均可通过规避设计、替换、合规改造或付费许可解决。

# 九、结论与边界

结论：采纳「三轨并行 + 三门控」模型——工程加固线（P0 必做，P1 强烈建议，P2/P3 按需）+ 商业预备线（M1–M3 提前测付费意愿）+ 合规线（G0 合规门，商标/FTO/开源/隐私/密码/AI 并行推进）；D0 规模决策选路线 A（默认）或 B（大库需求明确时）；G0 + G2 + G2′ 三门控共同决定收费上线时机。

核心本地功能永久免费，付费只对托管与增值服务；数据可完整导出，取消订阅不锁定、不删除。

最短可行路径（强烈推荐）

1. 第 0 步（已完成）：代码库已内置墓碑、侧栏指纹、LRU、原型污染防御、加密兜底、多标签 LWW、XSS 防御、错误限流等 10+ 项防御性优化，无需重复排期（详见附录 B）。

2. 本周：16 项启动清单全部启动。

3. 第 1–2 周：完成 P0（结构共享 + 历史栈增量）→ 20k–30k 节点流畅，打字无感。

4. 第 3–10 周：M1 架构拆分（4–6 周）+ 并行 B1/B2 商业前置 + C1/C2/C3 合规前置。

5. 第 11–18 周：M2 渲染替换 + M3 测试 + P1a/P1b（增量落盘/索引）+ B3 waitlist 内测 + C4/C5/C6 合规推进。

6. 第 19–26 周：M4 分发合规 + B4 支付就绪 + G0 合规门通过，G2 + G2′ 双门控。

7. 第 27 周起：M5 商业化上线 + 用户验证 3 轮。

## 影响

若按最短路径执行，最早可在 第 5 个月（M3 结束）启动内测收费试点，第 7 个月正式上线。

3 万节点规模在 P0 完成后即达「长期大量写作」标准；10 万节点需 P1 全部完成。

总工期 7 个月（乐观）/ 9–10 个月（现实）；预算 期望 ¥7–11 万，区间 ¥4.3–17 万（含合规）。

合规线若 G0 不通过，收费上线不得启动；商标被占用可能触发改名，影响品牌与商店素材，需预留 2–4 周缓冲。

## 是否彻底影响商业化？仅自用？

| 情形 | 结论 |
| --- | --- |
| 高风险专利不规避、不许可 | 公式引擎、数据库多视图的该功能商业化风险高，可能被诉、被要求许可费、被申请禁令 |
| 高风险专利规避或许可 | 可继续商业化，但需成本与时间 |
| 中风险专利规避 | 可商业化，但需改造 |
| 低风险专利 | 基本不阻断 |
| 商标、开源、隐私、商用密码不合规 | 可能被下架、罚款、诉讼，面向公众商业化前必须处理 |
| 仅自用（个人、不公开、不分发、不经营） | 专利 FTO 与商标风险极低；开源不分发通常不触发；隐私个人/家庭事务通常不适用；商用密码一般不涉及 |

一句话

现有 JU 的瓶颈不在存储，在运行时。P0 两项改造（1.5 周）投入产出比最高；10 万节点流畅需 P0 + P1 全部完成（约 8 周）。商业化不等工程全做完——用 waitlist 提前测付费意愿，用 G0 + G2 + G2′ 三门控决定收费时机。唯一不可跳过的是 M1 架构拆分；唯一不可压缩的是用户验证循环与签名/公证/商标的日历时间；唯一不可忽视的是合规前置门。

## 边界

工期与成本均为单人+AI协作、兼职投入假设下的估算。

性能数字为规划目标（基于代码盘点与业界同类操作基准），非实测值；上线前须用大库基准夹具实测验证。

转化率、留存、NPS 为规划目标而非实测。

未含团队扩张、融资、多平台适配等变量。

路线 B 的推进以 G2′ 规模门不通过为触发条件，非默认执行。

专利 FTO 结论基于 2026-10-07 检索结果，法律状态、同族、保护期与权利要求原文需由专利律师核验；本报告不构成法律意见。

商标检索结论待第 9 类补充；若核心类别被占用，需改名或购买，预算与工期另计。

开源许可、隐私、商用密码、AI 代码结论需在 SBOM、合规评估与 SCA 查重完成后更新。

地图视图已删除，原最高风险解除；残留常量、投影函数、入口需清理。
