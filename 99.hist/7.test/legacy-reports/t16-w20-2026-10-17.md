## 一、动因与范围

- **动因**：L16-W2 引入独立日历数据代次正是为「日历待办不变时不整表重建」；而索引层失败出口把「索引层降级」与「日历数据变化」混为一谈，使非日历索引（tag / searchInverted / backlinkMap / injection）失败也支付整表重建成本。
- **范围**：仅 [`canonical`](../../6.P0-L3基线/v2.0-l3.html.html:1) + step9 镜像 + 登记 / 门禁口径 + N 层用例 / 证据 / 波报告；**不新增纳编物**（登记方数保持 **43**）。

## 二、实现

### 2.1 统一失效入口（新增 · 定义于 `invalidateCalIndex()` 之后）

```js
function invalidateCalIndexOnly(){
  if(_calIndexCache===null)return false;
  _calIndexCache=null;
  _calDataRev++; /* L16-W2: _calIndexCache 实际置空 → 推进日历数据代次 */
  return true;
}
```

### 2.2 收口对照

| 接缝 | 改前 | 改后 |

> **决策记录 L16-W20-D1（代次判据单一化：以缓存实存性为唯一信号）**：① 「日历数据是否变化」与「索引层是否降级」是两个正交事实，`_calDataRev` 只应由前者推进；在 7 处索引失败出口上，「日历索引已被置空」恰是「已推进过代次」的充分代理信号（`invalidateCalIndex()` 与 `initStore` / 桌面重载路径均在置空同址推进），故以 `_calIndexCache===null` 作为幂等门控（null → null 无需二次推进）。② **连败分支（`streak>=3`）首次命中仍会推进一次代次**（该分支的语义是「强制 4 索引全量重建」，日历索引确实被置空）；此后在日历索引被重建前，重复失败不再推进 —— 实测连续 5 次失败 `_calDataRev` **仅 +1**，`_renderDayCache` 由 5 次重建降为 **1 次**。③ 日历数据真实变化路径（`setNodeDate` / `moveToTrash` / `invalidateCalIndex` 等）**不受门控影响**，仍无条件递增，日历视图正确性不退化。④ 返回布尔值仅供内部 / N 层观测，不构成公开 API。
> **降级 / 契约**：`state.nodes` 结构、`juju.store.v31` 序列化形状、加密 payload 字段名零变更；公开 API（`window.__juIndexShadow` / `window.__juPersistProbe` / `window.__juL9Shadow` / `window.__juL10D1`）零变更；`__l14On()` / `_vsUserDisabled` / `IS_DESKTOP` 分支不涉及（本组函数无优化开关）；非优化分支（4 索引 lazy full rebuild 兜底、连败阈值 3、FIFO 50 失败环形缓冲）逐字保留；**不新增 `<script>` 块**（9 块 · 语法检查全通过）。
> **注释保全**：本次仅替换「描述已被移除行为」的 3 处 L16-W2 行内注记（其语义已由新 helper 的注释承接），未批量清理任何 `FIX-XXX-N` 历史编号注释。
